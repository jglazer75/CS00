# CS00 Platform: System Observations Report
*Date: February 20, 2026 | Author: Claude Code (claude-sonnet-4-6)*

---

## I. Problem Statement

In a few weeks, a full classroom of students will hit this platform simultaneously for the first time. The system has never operated under real human load or real human confusion. The core problem is not performance — it is **readiness**: access control is incomplete, security assumptions made during development are not production-safe, the line between "browse content" and "do required work" is invisible to a student, and the AI layer is wired for developer-ergonomics rather than classroom-ergonomics.

The secondary problem, which is related but distinct, is architectural: the platform was built incrementally on top of an earlier version, and the seams show in ways that will create operational friction at scale.

## III. Alignment with User Observations

### Observation 1: Students may not know which pages are informational vs. required

**Confirmed.** The `module.yaml` manifest has both a `type` field (`page`, `section`, `ai-interaction`) and a `layout` field (`reader`, `workbench`). These differentiate the nature of each page architecturally, but neither value surfaces in the UI. The navigation renders all nodes as identical links. A student looking at the CS01 nav would not know that "Foundations" is background reading while "Redlining Exercise" is required coursework with an AI submission component.

This is a UX fix, not an infrastructure fix. The data is already there in the manifest; it just needs to be rendered.

### Observation 2: AI access should be permissioned; Guest On/Off; ACL

**Confirmed and extended.** Currently, access works like this:
- Unauthenticated users: appear to be able to view content (no middleware redirect), but `progressStatus === 'unauthenticated'` is handled gracefully in the UI
- Authenticated users: can use all AI features with no additional check
- The "guest" concept does not exist in code — it is implied by the unauthenticated state but never explicitly managed

What the platform needs is a three-tier model:
1. **Guest** — can browse content, cannot use AI, cannot track progress
2. **Student** — authenticated, progress tracked, AI access controlled by instructor
3. **Instructor / Admin** — full access plus privileged views

The "AI On/Off" toggle is the most immediate need. The platform already has an `ADMIN_EMAILS` env-var mechanism for admin detection. A similar lightweight flag (`ai_enabled` on the user record, or an `ai_access` group in Supabase) would satisfy this without requiring a full RBAC build.

### Observation 3: Page and module permissioning — probably not worth building a full system now

**Agreed, with a caveat.** The `module.yaml` already has `visibility: role: [...]` fields defined. They are read by the ingest pipeline and stored in `module_nodes` metadata. The enforcement work is not "build a permissioning system" — it is "read the role field from the node already in the database and filter the response." This is a few lines of code, not a project.

The caveat: the role assignment for users does not exist yet. For the immediate term, roles can be implicit (instructors = admin emails, BigTech = a separate invite group or manually assigned). A full RBAC build is unnecessary; a pragmatic shortcut that handles the CS01 role structure is sufficient.

### Observation 4: The AI system — is it the correct implementation?

**Partially.** The gateway architecture is sound. The concerns are:

**What is correct:**
- The task-definition JSON schema (`AiTaskDefinition`) is genuinely good. It decouples authoring from code, allows instructors to configure exercises without engineering involvement, and supports complex prompt construction with conditionals, context injection, and toggles. This should be kept.
- The provider-agnostic adapter pattern is forward-looking and architecturally clean.
- The prompt-hash caching in Postgres is appropriate for this scale.
- The `NegotiationSimulator` (DealCraft) stateful multi-turn approach — storing history in the `negotiations` table with `current_state` as a running deal state — is exactly right for the use case.

**What is wrong:**
- **The BYOK model is wrong for the classroom.** Students are not likely to have Gemini API keys. The `app/settings/ai/page.tsx` presents a form asking users to configure their own API key, which will confuse students and adds operational overhead. The system key should be the default and only option for students. BYOK should be an instructor-only or module-admin feature.
- **API keys are not encrypted.** The column is named `encrypted_api_key` but the settings page has a comment acknowledging this is not implemented. This is a security liability for any instructor who provides a key.
- **The settings UI is surfaced as a top-level user-accessible page** when it should be hidden for student accounts.
- **The AI gateway mixes concerns.** Provider resolution, cache checking, file extraction, negotiation state management, data capture, and telemetry are all in a single 300-line route handler. This is manageable now but will become difficult to debug when classroom-scale issues surface. Factoring negotiation state management into its own service would help.

**On alternative implementations:**
The Vercel AI SDK (`ai` package) provides streaming, multi-turn conversation management, tool calling, and multi-provider support natively, and would replace most of the custom adapter and history management code. However, migrating to it now would be significant scope and would require rewiring the NegotiationSimulator and DocumentAnalyzer. The recommendation is: **keep the current architecture, simplify the student-facing surface (hide BYOK), fix the security issue, and revisit the AI SDK as a future enhancement.**

### Observation 5: The module system — take opinions

**The system is fundamentally sound but has one active split that needs to be healed.**

The `module.yaml` → `scripts/ingest.ts` → Supabase `module_nodes` pipeline is the correct architecture. It is declarative, DB-driven, and supports the full feature set (layouts, visibility, AI task anchors, structured navigation).

The problem: the dashboard (`app/page.tsx`) still calls `getSortedPagesData()`, which reads directly from the filesystem rather than from the database. This path bypasses the manifest entirely. It means the dashboard is not aware of module structure, layouts, or visibility rules — and will diverge from the rest of the app whenever a `module.yaml` is updated but the filesystem doesn't match.

The `module_pages` table in `schema.sql` also appears to be a predecessor to `module_nodes` (added in migration `20260114204147`). It's unclear whether `module_pages` is still used anywhere or is dead code.

**Recommendation:** Retire `getSortedPagesData` from the dashboard. Replace with a Supabase query against `modules` (for the title/description) and drive module metadata from the manifest. The filesystem read path should exist only as a development fallback when the database is unavailable.

## IV. Code Observations

The following are findings from direct code review, independent of the provided observations.

### IV-1. No authentication middleware
There is no `middleware.ts` in the `learning-platform/` directory. In Next.js App Router, this is the standard mechanism for redirecting unauthenticated users. The absence means:
- Module pages are accessible without login
- The AI settings page is accessible without login
- The admin invite page relies on a client-side admin check (which is also exploitable)

The existing `progressStatus === 'unauthenticated'` handling in `ModulePageContent.tsx` suggests the dev experience was intentional (useful for testing), but this must be gated for production.

### IV-2. InstructorMode is client-side state only
`InstructorModeContext` is a React state toggle. There is no server-side verification that the toggling user is actually an instructor. The `InstructorNoteCard` is conditionally rendered in the client component based on this state. An adversarial student could read instructor notes by manipulating client state. The check must move server-side.

### IV-3. module.yaml visibility rules are parsed but never enforced
`content/CS01/module.yaml` contains:
```yaml
- id: "confidential-bigtech"
  visibility:
    role: ["BigTech", "Instructor"]
```
and
```yaml
- id: "instructor-resources"
  visibility:
    role: ["Instructor"]
```

`getModuleStructure()` and `getModulePages()` in `lib/content.ts` return ALL nodes without filtering by visibility. The `module_nodes` DB table stores `metadata` (which would contain the visibility field after ingest), but there is no filtering step in the query or the tree-building logic. Every user sees and can access every page, regardless of role.

### IV-4. `encrypted_api_key` is not encrypted
`app/settings/ai/page.tsx`, line 53:
```typescript
encrypted_api_key: apiKey, // Note: In production, encrypt this client-side or send to API to encrypt!
```
The column name implies encryption; the implementation does not provide it. Any API key stored by any user is in plaintext in Supabase.

### IV-5. Two content pipeline paths coexist
- `getPageData()` / `getModuleStructure()` → queries `module_nodes` table (correct, DB-driven)
- `getSortedPagesData()` → reads markdown files from filesystem directly (legacy, bypasses YAML)

`app/page.tsx` (dashboard) uses `getSortedPagesData()`. This means the dashboard does not reflect the `module.yaml` structure and will silently diverge from the rest of the application.

### IV-6. Dashboard title is hardcoded
`app/page.tsx`, line 15:
```typescript
title: `Venture Capital Term Sheet`, // hardcoded
```
Module title and description are defined in `module.yaml` and ingested into the `modules` table. The dashboard should read from there.

### IV-7. Development artifact in production navigation
`content/CS01/module.yaml` includes:
```yaml
- id: "test-ai"
  title: "AI Gateway Test"
  content_source: "99-test-ai.md"
```
This node has no `visibility` restriction and will appear in the nav for all students.

### IV-8. No rate limiting on the AI gateway
`app/api/ai/route.ts` has no per-user, per-minute, or per-day call limiting. For a classroom of 25+ students simultaneously running multi-turn NegotiationSimulator sessions, API costs could spike significantly in a single class period. Gemini Flash is cheap but unbounded concurrency still adds up, and there is no circuit breaker.

### IV-9. `ai_request_cache` RLS blocks the gateway
`schema.sql` defines this policy for the cache table:
```sql
create policy "Service role manages AI cache"
  on public.ai_request_cache
  for all
  using (auth.role() = 'service_role')
```

The AI gateway uses `getSupabaseServerClient()` which should use the service role if `SUPABASE_SERVICE_ROLE_KEY` is set. If it falls back to the anon key, all cache writes will silently fail and every request will be a cache miss. This depends on environment configuration and should be verified.

### IV-10. Admin access check uses client-exposed env var
The invite page checks `isAdminEmail(user.email, 'public')`, which reads from `NEXT_PUBLIC_ADMIN_EMAILS` — a value embedded in the client bundle. While the actual invite API route has server-side verification, the client-side check means the admin email list is visible to any user who inspects the JS bundle.

### IV-11. Bulk student management is missing
Students must be invited one at a time via `/admin/invite`. A semester-start cohort of 20-30 students would require 20-30 manual invite operations. There is no CSV upload, no link-based self-enrollment, and no roster view.

### IV-12. No instructor visibility into class progress
The `user_module_progress` table collects per-student, per-page progress, and `user_module_state` tracks overall completion percentages. However, there is no admin/instructor view that aggregates this data. An instructor cannot see which students have completed which exercises.

## V. Synthesis: The System As It Would Exist After Solutions

If the initial solutions, user observations, and code observations are addressed, the platform transforms as follows:

**Access control** becomes a real mechanism: unauthenticated users are guests (browse only), authenticated students have scoped access (AI on/off by instructor), and instructors have verified server-side elevation. The module.yaml visibility rules are enforced, so BigTech briefings are only visible to BigTech-role users.

**The AI layer** becomes classroom-appropriate: students see the system key as the default (no BYOK confusion), AI access is a permissioned feature the instructor can toggle, and API keys are stored securely. The gateway architecture itself remains intact.

**The module system** becomes coherent: a single pipeline (manifest → DB → UI), with the dashboard reading from the same source as the module pages. The dev artifact is removed. Page types are visually differentiated so students know what is required.

**Operations** become manageable: bulk invite, a class progress dashboard, and rate limiting that prevents cost surprises.

The residual risk is the architectural seam between the one-shot `DocumentAnalyzer` and the stateful `NegotiationSimulator` within a unified gateway. This is not a blocker for classroom launch but will be the most likely source of hard-to-debug issues. Monitoring on `ai_task_runs` is the mitigation.
