## Scoring Rubric

Each proposal is scored on three axes:

| Axis | Scale | Definition |
|------|-------|------------|
| **Urgency** | 1–5 | 5 = must be done before first classroom session; 1 = can wait indefinitely |
| **Impact** | 1–5 | 5 = affects every student every session; 1 = narrow edge case |
| **Effort** | 1–5 | 1 = under 2 hours; 2 = half-day; 3 = 1–2 days; 4 = 3–5 days; 5 = 1+ week |

**Priority Score** = `(Urgency + Impact) × (6 − Effort)` — higher is better. This rewards high-impact, low-effort work and penalizes high-effort work for problems that aren't urgent.

**Tiers:**
- **Launch Blocker (LB):** Must be done. Platform should not go live without it.
- **Pre-Launch (PL):** Strongly recommended before the first class session.
- **Post-Launch (PO):** Can be done after launch but should be scheduled.
- **Defer (D):** Good idea but not time-sensitive.

### P1 — Authentication Middleware (Route Protection)

**Problem:** No `middleware.ts` exists. Module content, AI settings, and admin pages are accessible without authentication. The invite page has a client-side admin check only.

**Proposed Solution:** Add `middleware.ts` to the `learning-platform/` root using the `@supabase/ssr` package. Route access model:

| Route | Unauthenticated | Authenticated |
|-------|----------------|---------------|
| `/` | ✅ Public — browse module listing | ✅ |
| `/login`, `/reset-password` | ✅ Public | ✅ (redirect away) |
| `/modules/[moduleId]/*` | ↩ Redirect to `/login` | ✅ (module page enforces public/private — see PMD) |
| `/settings/*` | ↩ Redirect to `/login` | ✅ |
| `/admin/*` | ↩ Redirect to `/login` | ✅ (admin pages enforce role) |

Middleware is responsible only for the auth boundary. Whether an authenticated user can access a specific module (public vs. private enrollment) is enforced in the module page server component, not in middleware.

**Scope:** One new file (~40 lines), configuration of public vs. protected paths.

**Dependencies:** None. Supabase client is already configured.

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 5 | Without this, students who lose their session token can still navigate to protected content |
| Impact | 5 | Affects the entire application |
| Effort | 1 | Standard Next.js middleware pattern; Supabase Auth Helpers have a ready-made example |
| **Priority Score** | **50** | `(5+5) × (6−1)` |

**Tier: Launch Blocker**

### P2 — AI Access Permissioning

**Problem:** Any authenticated user can call `/api/ai`. There is no instructor-controlled on/off switch, no guest-mode AI block, and no access control list.

**Proposed Solution:**

Add a `profiles` table (or extend Supabase `auth.users` with `user_metadata`) with an `ai_enabled` boolean. Default: `false`. Instructor/admin can flip this to `true` for individual students or set a module-level default.

In the AI gateway route, after authentication, add a check:
```typescript
const { data: profile } = await supabase
  .from('profiles')
  .select('ai_enabled')
  .eq('user_id', user.id)
  .single();

if (!profile?.ai_enabled) {
  return NextResponse.json({ error: 'AI access not enabled for this account' }, { status: 403 });
}
```

Admin UI: add a toggle to the `/admin/modules` page (or a new `/admin/users` page) to enable/disable AI per user or bulk-enable all users.

The "Guest" mode is satisfied by the auth middleware (P1): unauthenticated = guest = no AI access.

**Scope:** One DB migration (profiles table or user_metadata), ~10 lines in the gateway, admin toggle UI.

**Dependencies:** P1 (auth middleware should be in place first).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 5 | Without this, you cannot control which students get AI access |
| Impact | 4 | Directly controls the most expensive and pedagogically sensitive feature |
| Effort | 2 | DB migration + gateway check is small; admin UI adds complexity |
| **Priority Score** | **36** | `(5+4) × (6−2)` |

**Tier: Launch Blocker**

### P2T — Team & Group Management

**Problem:** The NegotiationSimulator currently lets students freely choose their side (NewCo or BigTech). In a classroom, multiple students could pick the same role, breaking the adversarial structure. More broadly, the platform has no concept of student groups — which is foundational to how CS01 and future modules are pedagogically structured.

**Proposed Solution:**

**Data model** (two new tables, added to the same migration as the `profiles` table from P2):

```sql
-- Teams within a module
CREATE TABLE public.teams (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  module_id text NOT NULL REFERENCES public.modules(id) ON DELETE CASCADE,
  name text NOT NULL,
  role text,  -- module-defined role e.g. "NewCo", "BigTech"; null until assigned
  created_by uuid REFERENCES auth.users(id) ON DELETE SET NULL,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

-- Team membership
CREATE TABLE public.team_members (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id uuid NOT NULL REFERENCES public.teams(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  created_at timestamptz DEFAULT now(),
  UNIQUE (team_id, user_id)
);
```

One team per student per module is enforced at the application layer: when adding a user to a team, the API removes any prior membership for that user in the same module before inserting.

**Team creation — two modes:**

*Random:*
`POST /api/admin/teams/generate`
```json
{
  "moduleId": "CS01",
  "by": "numTeams",
  "value": 5,
  "assignRolesRandomly": true
}
```
Server: fetch all non-instructor enrolled users → shuffle → split into N equal teams (or by students-per-team) → if `assignRolesRandomly`, distribute available module roles round-robin across teams.

*Direct (manual):*
Admin UI presents the enrolled roster and a set of team buckets. Instructor assigns students to teams by selecting from a list. Each team gets a role from a dropdown.

**Admin UI:** New page at `app/admin/modules/[moduleId]/teams/page.tsx`
- Shows current teams for the module with their role and member list
- "Generate Teams" dialog: choose random config (by # teams or # per team) and whether to randomize roles
- Manual assignment: select-and-assign interface for both students → teams and teams → roles
- Populated module roles from `module.yaml` `roles` field (read from `modules` table or YAML)

**NegotiationSimulator integration (`app/components/ai/NegotiationSimulator.tsx`):**
- On load, query `team_members → teams` to find the user's team role for the current module
- If role found: skip the role-selection UI; show "You are representing [role]" and proceed directly
- If not found: fall back to current manual selection (current behavior preserved)

**Effect on P4:** This eliminates the need for a separate `user_roles` table. A user's module role is derived from their team record. See updated P4 below.

**Scope:** One migration (teams + team_members), one new API route (`/api/admin/teams/generate`), new admin UI page, ~20 line change to `NegotiationSimulator.tsx`.

**Dependencies:** P2 (profiles table and admin user list must exist; teams UI builds on the same admin area).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 4 | Simulator falls back to manual selection without it, but pedagogical intent is broken |
| Impact | 5 | Affects core exercise mechanic for every student every session |
| Effort | 4 | Schema is simple; generation API + admin UI + simulator integration span several files |
| **Priority Score** | **18** | `(4+5) × (6−4)` |

**Tier: Pre-Launch** — Built concurrently with P2 as a single combined workstream (same migration, same admin area).

### P3 — Fix API Key Storage / Simplify AI Settings

**Problem:** `encrypted_api_key` stores plaintext API keys. The student-facing settings page presents the BYOK model (bring your own key) which is inappropriate for a classroom. An instructor who configures a key exposes it in plaintext.

**Proposed Solution (two parts):**

**Part A — Simplify the student UI:**
Remove or hide `app/settings/ai/page.tsx` from student-role users. The system Gemini key (configured via `GEMINI_API_KEY` env var on Vercel) should be the classroom default. Students do not need to — and should not — configure API keys.

**Part B — Secure key storage for admin use:**
Rename the column from `encrypted_api_key` to `api_key` (or actually encrypt it). For the classroom deployment, if only the system key is used, Part B is lower priority. However, if an instructor wants to configure a per-module key (which `module_ai_settings` supports), the key should be encrypted server-side using Supabase Vault or a simple AES encryption with a key stored in env vars.

**Scope (Part A):** Role-check on the settings page render (~5 lines). Part B: encryption utility + migration.

**Dependencies:** P2 (need role concept to hide settings from students).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 5 | Security issue is pre-launch; student confusion from BYOK is a UX issue that will generate support overhead |
| Impact | 3 | Primarily affects instructor keys; system key users are unaffected by storage issue |
| Effort | 2 | Part A is trivial; Part B adds 1 day for proper encryption |
| **Priority Score** | **32** | `(5+3) × (6−2)` |

**Tier: Launch Blocker** (Part A); Pre-Launch (Part B)

### P4 — Enforce module.yaml Visibility Rules

**Problem:** The `visibility: role: [...]` fields in `module.yaml` are parsed and stored but never evaluated. The BigTech briefing and all instructor resources are visible to every authenticated user.

**Proposed Solution:**

With P2T in place, no separate `user_roles` table is needed. A user's module role is derived from their team membership:

```typescript
// In the module page server component, before calling getModuleStructure():
const { data: teamData } = await supabase
  .from('team_members')
  .select('teams!inner(role)')
  .eq('user_id', user.id)
  .eq('teams.module_id', moduleId)
  .maybeSingle();

const userModuleRoles: string[] = [];
if (profile?.is_instructor) userModuleRoles.push('Instructor');
if (teamData?.teams?.role) userModuleRoles.push(teamData.teams.role);
```

In `lib/content.ts`, modify `getModuleStructure()` to accept a `userRoles: string[]` parameter and filter the node tree:
```typescript
function nodeIsVisible(node, userRoles: string[]): boolean {
  const visibility = (node.metadata as any)?.visibility;
  if (!visibility?.role) return true; // no restriction
  return visibility.role.some((r: string) => userRoles.includes(r));
}
```

**Note on `module_nodes` metadata:** Verify `scripts/ingest.ts` writes the `visibility` field from `module.yaml` into the `module_nodes.metadata` jsonb column. If it does not, fix ingest first.

**Scope:** ~20 lines in content.ts, ~10 lines in the page route. No new DB migration beyond P2/P2T.

**Dependencies:** P2T (teams + team_members tables must exist).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 5 | Instructor content is currently visible to all students |
| Impact | 4 | Protects confidential materials; makes the BigTech exercise work as designed |
| Effort | 3 | Moderate — needs ingest verification, content.ts update, role assignment UI |
| **Priority Score** | **27** | `(5+4) × (6−3)` |

**Tier: Launch Blocker**

### P5 — Fix InstructorMode to be Server-Verified

**Problem:** `InstructorModeContext` is client-side state. Any user can toggle instructor mode in the browser console. Instructor notes are exposed client-side and conditionally rendered based on this state.

**Proposed Solution:**

Instructor notes are loaded server-side in `getPageData()` via `loadInstructorNote()`. The fix has two parts:

1. Pass the user's role from the server to the client component (via a prop or the existing session context).
2. In `ModulePageClient.tsx` / `ModulePageContent.tsx`, derive `isInstructorMode` from the server-verified role rather than the context toggle. The context can remain for the toggle UX, but should be initialized from a server-provided `isInstructor` prop, not from a default `false` that any user can flip.
3. The instructor note HTML should not be included in the page payload for non-instructor users (i.e., `loadInstructorNote` should return `undefined` unless the user has the Instructor role).

**Scope:** ~20 lines across `content.ts`, the page route, and `ModulePageContent.tsx`.

**Dependencies:** P4 (user_roles table).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 4 | Students could read instructor notes if they know to look |
| Impact | 3 | Affects instructor note confidentiality specifically |
| Effort | 2 | Small targeted change once roles exist |
| **Priority Score** | **28** | `(4+3) × (6−2)` |

### P7 — AI Rate Limiting

**Problem:** No per-user or global call limits on the AI gateway. A classroom of students running simultaneous NegotiationSimulator sessions could generate unbounded API costs in a single class period.

**Proposed Solution:**

Add a lightweight rate limiting check at the top of the gateway route using a Redis-free approach (Postgres-backed, using `ai_task_runs` which already exists):

```typescript
const oneHourAgo = new Date(Date.now() - 60 * 60 * 1000).toISOString();
const { count } = await supabase
  .from('ai_task_runs')
  .select('id', { count: 'exact', head: true })
  .eq('user_id', user.id)
  .gte('created_at', oneHourAgo);

if (count && count > RATE_LIMIT_PER_HOUR) {
  return NextResponse.json({ error: 'Rate limit exceeded. Please wait before making more requests.' }, { status: 429 });
}
```

`RATE_LIMIT_PER_HOUR` should be an env var, defaulting to a reasonable classroom value (e.g., 20–30 calls/hour per user).

This does not require Vercel KV or Redis. `ai_task_runs` is indexed on `user_id`.

**Scope:** ~15 lines in the gateway route.

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 3 | Important but Gemini Flash is cheap; 25 students unlikely to cause a bill emergency in a 3-hour class |
| Impact | 3 | Primarily cost protection; also prevents one student from consuming all capacity |
| Effort | 1 | Trivial to implement |
| **Priority Score** | **30** | `(3+3) × (6−1)` |

### PMD — Module Access Control (Public / Private)

**Problem:** All modules are currently accessible to any authenticated user. The platform needs two access modes: **public** (any logged-in user can work through the module freely) and **private** (only users explicitly enrolled by a teacher or the module creator can access it). The module listing at `/` should be browsable without login, but entering a module requires authentication and — for private modules — enrollment.

**Proposed Solution:**

**Schema changes** (added to the P2+P2T migration):

```sql
-- Add access mode to modules table
ALTER TABLE public.modules
  ADD COLUMN is_public boolean NOT NULL DEFAULT false;

-- Explicit enrollment for private modules
CREATE TABLE public.module_enrollments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  module_id text NOT NULL REFERENCES public.modules(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  enrolled_by uuid REFERENCES auth.users(id) ON DELETE SET NULL,
  enrolled_at timestamptz DEFAULT now(),
  UNIQUE (module_id, user_id)
);
ALTER TABLE public.module_enrollments ENABLE ROW LEVEL SECURITY;
```

**Access check** in module page server component (`app/modules/[moduleId]/page.tsx` and `[slug]/page.js`):

```typescript
const { data: mod } = await supabase.from('modules').select('is_public').eq('id', moduleId).single();

if (!mod?.is_public && !profile?.is_instructor) {
  const { data: enrollment } = await supabase
    .from('module_enrollments')
    .select('id')
    .eq('module_id', moduleId)
    .eq('user_id', user.id)
    .maybeSingle();
  if (!enrollment) redirect('/');
}
```

**Team assignment auto-enrolls (P2T integration):** When a teacher assigns a student to a team for a module (via the teams admin UI), the API also inserts an enrollment record. Students don't need to be enrolled separately from being assigned to a team — the two operations are atomic.

**Admin UI** (on the module admin page, alongside team management):
- Toggle public / private per module
- For private modules: enrollment list showing who has access and who granted it
- Bulk enroll from the roster (for modules without teams, or for students who need access before team assignment)

**Instructor access:** Instructors always bypass the enrollment check — they can access all modules regardless of public/private setting.

**Scope:** Small schema addition to the P2+P2T migration, ~15 lines in each module page route, admin toggle, enrollment API.

**Dependencies:** P2+P2T (profiles, teams, and the admin area must exist; auto-enrollment hooks into team assignment).

| Axis | Score | Notes |
|------|-------|-------|
| Urgency | 4 | Without this, CS01 must be public for all authenticated users — workable short-term but not the intended model |
| Impact | 4 | Determines who can access what content |
| Effort | 3 | Schema is simple; page check is trivial; admin UI is an addition to P2T teams page |
| **Priority Score** | **24** | `(4+4) × (6−3)` |

**Tier: Pre-Launch** — Built concurrently with P2+P2T as part of the same admin workstream.

## Recommended Launch Sprint

If time permits only one sprint before the first classroom session, the following constitute the minimum viable production state:

1. **P1** — Auth middleware (hours)
2. **P9** — Remove test-ai artifact (minutes)
3. **P2 + P2T** — Profiles + Teams (combined workstream, ~2 days — one migration, parallel UI; P2T builds on P2's admin area; both unblock P3, P4, P5)
4. **P3a** — Hide BYOK settings from students (minutes once P2 profiles exist)
5. **P4** — Enforce visibility rules (half-day — no new migration needed; derives roles from P2T teams)
6. **P7** — Rate limiting (1 hour)

**P6** (page type UX) and **P8** (pipeline consolidation) are the highest-return items for the second sprint.
